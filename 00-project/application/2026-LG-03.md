# Low-Cost Headless CMS and Static Site Generator

## My interpretation of the brief
I interpret this topic as a system that separates content management from the public website and generates static pages from stored content. Content editors would manage pages and articles through an administration interface without editing source code. A generation process would combine published content with templates to produce a deployable static website. The objective would be to keep public-site hosting inexpensive while providing a straightforward editing and publishing workflow. I would confirm the detailed requirements and technology constraints against the full published brief before finalising the specification.

## Why I am a good fit for this project
I would approach this project by focusing on a small, complete workflow: creating content, previewing it, publishing it, and viewing the generated website. This provides a manageable scope while still requiring careful work on the user interface, content modelling, backend access, and page generation. The project also offers concrete results to demonstrate and evaluate, including publishing correctness, generation time, and the cost of the proposed deployment.

## Relevant experience and background
I have established a GitHub repository for my project documentation and future source code. I would use this project to develop and demonstrate skills in web interfaces, API design, structured content storage, template rendering, and automated testing. My application does not rely on claims of previous professional CMS development; I would address unfamiliar technologies through focused prototypes and document the decisions made during the planning phase.

## Proposed approach
I would first define a minimal content model for pages and articles, including titles, unique slugs, content, and draft or published status. I would then prototype the generation process using a small set of templates and test that only published content appears in the output. An authenticated administration interface would provide content creation, editing, preview, and publishing, with validation and restricted access to editing operations.

Subject to the published brief, I would propose TypeScript for the application and generation logic, a lightweight backend with persistent content storage, and static hosting for the generated HTML, CSS, and assets. The first complete version would support a single website and a limited set of content types. A failed build should preserve the previously published site. I would evaluate hosting costs for both the administration backend and the public website rather than treating static hosting alone as the total cost. Multi-site management, a plugin marketplace, and a visual page builder would remain outside my proposed initial scope.
